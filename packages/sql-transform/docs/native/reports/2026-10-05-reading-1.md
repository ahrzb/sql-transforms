# Native catalog, reading 1 (2026-10-05)

## 0. What this is {#what-this-is}

This is the native-transform catalog's first milestone report. It was taken
on master `b926e88` on 2026-10-05, plus this report's own measuring tools
(`benchmarks/bench_native.py`, `coverage --modules` and the
`NATIVE_SEEDS` variable), which change nothing the catalog serves.

There is no previous report. Deltas are against the loop's start that
morning, when only `StandardScaler` was native (1 of 68).

The milestone covers three things:
- a batch of five families: scalers, imputers, selectors,
  `PolynomialFeatures` and encoders;
- a whole sklearn module native: `sklearn.feature_selection`;
- nine catalog needs served by confit, in seven PRs.

Every number below was measured on that tree, with confit's release build,
using the commands in [section 8](#environment-and-repro).

## 1. What moved {#what-moved}

**A third of sklearn's in-scope transformers serve natively, all
bit-exact.**
- 23 of 68 are native, up from 1 that morning: six scalers, two imputers,
  eleven selectors, `PolynomialFeatures` and three encoders.
- Every entry is registered at 0 ulps and is held there by the
  swap-the-entry check.
- Over 200 seeds of every fixture configuration, 11,933 steps
  matched their twins bit for bit, with no breach. Another 67
  steps stayed Python by a named cap ([section 4](#exactness)).

**A native entry serves a 64-row call 3x to 373x faster than its Python
twin.** This is measured on each class's widest fixture step.
- The widest steps are 21 to 276 lanes wide.
- A native call takes 29 to 6,092 µs. The twin takes 7,555 to 153,874 µs
  for the same call.
- The twin pays sklearn's input validation on every row. A selector or an
  encoder does little else, so those gain the most: 93x to 373x for
  selectors, and 41x to 369x for encoders.

**`sklearn.feature_selection` is entirely native.** All eleven selectors
inherit `SelectorMixin.transform` without overriding it. One translator
therefore serves them all: the kept columns, unchanged, taken from the
fitted mask.

**Categorical features serve natively.** `OrdinalEncoder`, `OneHotEncoder`
(dense) and `TargetEncoder` translate by asking the fitted twin for each
class's output: each fitted category, missing, and unknown. Infrequent
categories, `drop`, `handle_unknown` and target means are therefore the
twin's own values. Every encoder fixture includes string features with
unseen values and NULLs.

**confit served nine catalog needs in one day, in seven PRs.** Each came
from the catalog's "Needs from confit" list with a repro
([section 6](#needs-from-confit)).
- A 128-feature `StandardScaler` with three groups used to hit the token
  cap. It now builds in {{SS128}}.
- `PolynomialFeatures` over integer features used to build in 20 to 50 s
  (measured this morning). Its widest fixture now builds in 2.4 s
  ([section 3](#speed)).
- A 48-feature `Normalizer` used to crash Cranelift. confit now refuses it
  by name.
- Steps wider than 2,000 lanes now build instead of refusing, though
  slowly: 2,556 lanes take {{BUILD2556}}.

**A confit leak ends a process after about 32,000 builds.** This is new in
this reading, and open.
- Every build leaks two memory mappings and about 8 KB that are never freed.
- At Linux's default cap of 65,530 mappings, the process stalls, or fails
  every build after that point.
- The 200-seed sweep met it in its test workers. A long-lived server that
  rebuilds functions would meet it too.
- It is sent to the confit loop (finding 19). Sweeps now run one class per
  process.

**Two confit limits still cap the catalog.**
- **No shared subexpression.** confit cannot evaluate a repeated
  subexpression once per call, so every `Normalizer` lane repeats the row
  norm.
  - Its native call is only 3x faster than the twin.
  - The max norm is capped at 8 features.
  - l1 and l2 stop building somewhere between 16 and 32 features.
- **Quadratic build time.** In the catalog's shape, build time grows
  quadratically in the lanes read: {{CURVE_SUMMARY}}.
  - The catalog's fixtures stop at 300 lanes.
  - `PolynomialFeatures` at its widest fixture (276 lanes) is only 5x
    faster than the twin.

## 4. Exactness {#exactness}

**All bit-exact.** Every registered bound is 0 ulps, across all 23 classes.

**The reading.** It covers 200 seeds for every fixture configuration, 60
configurations in all.
- 11,933 steps were each checked row by row against their twin,
  and against their own definition run on DuckDB.
- There were 0 breaches.
- 67 steps stayed Python by a named cap: 61 `Normalizer(norm="max")` steps past the 8-feature cap, and 6 `Normalizer` l1 or l2 steps past confit's compiled-size limit.

**The order helpers.** `_helpers_test.py` holds four of numpy's
operations bit for bit at widths 1 to 300: the pairwise sum, the einsum
kernel, `max` and `clip`. A wrong order fails 40 to 50% of rows at every
width.

## 5. Findings {#findings}

These were in the catalog and its tests:

| # | finding | what it was | how it was found | fixed in |
|---|---|---|---|---|
| 1 | `finding: clip-nan-guard` | DuckDB orders NaN above every number, so `x > hi` is true for NaN where numpy's comparison is false. sklearn's array-API clip therefore needs a NaN guard to keep NaN. | the order helpers, DuckDB against numpy | #329 |
| 2 | `finding: l2-norm-kernel-order` | `row_norms` sums its squares in the order of numpy's einsum kernel, not left to right. The x86-64 baseline kernel uses two lanes and an unfused multiply-add. A platform whose kernel differs is detected by a probe and left Python. | a wrong order failed 40 to 50% of rows at every width | #329 |
| 3 | `finding: fixture-int-rounding-marker` | The fixture generator rounded an integer column after scrubbing the imputer's missing-value marker, so rounding could bring the marker back. | building the imputer fixtures | #332 |
| 4 | `finding: blas-oversubscription` | Every xdist worker ran a multi-threaded BLAS. An `RFECV` fixture took 35 s instead of 0.4 s. | timing the selector fixtures | #340 |
| 5 | `finding: matvec-cancellation` | PCA scores `x·c - m·c`. Near the mean the two terms cancel, so no small ulp bound exists for any summation order but BLAS's own. Over 200 seeds the error reached 9.9e9 ulps, yet stayed within 2.99 eps of the term scale. | measuring a left-to-right PCA entry | open: `decisions/open/matvec-parity-bound.md` |
| 6 | `finding: duckdb-reference-per-lane` | The DuckDB reference in `check()` read a wide struct field by field, and DuckDB expands the macro at every read. A 285-lane struct took 18 s. | profiling slow polynomial fixtures | #343 (one call per row: 0.1 s, same answers) |
| 7 | `finding: encoder-all-missing-string` | A string feature that is missing in every fit row has categories `[None]`, which the encoder read as numeric. `OrdinalEncoder(use_encoded_value)` and `OneHotEncoder(ignore)` gave wrong answers. | a targeted test while reviewing the encoders | #347 (translators get the declared types) |
| 8 | `finding: fixture-shapes-shared` | Every configuration of a class drew the same 8 data shapes, so the column behind finding 7 never appeared. | asking why the fixtures missed finding 7 | #347 (each configuration seeds its own) |
| 9 | `finding: onehot-sparse-unservable` | The default `OneHotEncoder()`, with sparse output, cannot be served by the Python step either: the step calls `float()` on a sparse row. | translating the encoders | open: a step issue ([section 7](#left-open)) |

## 6. Needs from confit {#needs-from-confit}

**Delivered.** These are rows 10 to 18 above. What they unblocked:
- *#336:* serving a wide step without paying for every lane. #336 measured
  6.1 to 0.28 ms per 64-row call at 32 lanes; today a 27-lane
  `StandardScaler` call takes 264 µs ([section 3](#speed)).
- *#338, #339, #348:* wide steps build at all. A 128-feature, three-group
  `StandardScaler` builds in {{SS128}}, and `PolynomialFeatures` past 2,000
  lanes builds.
- *#341:* integer features build at the speed of DOUBLE ones, and deeply
  nested CASEs parse.
- *#346:* a named, catchable refusal where Cranelift corrupted a function.
- *#337:* not used by the catalog yet. The max norm keeps its tournament
  of two-way CASEs.

**Open.**
- **Free a build's compiled code when its function is dropped** (finding
  19). Any process that builds more than about 32,000 functions waits on
  it: a server that rebuilds, and the catalog's sweeps (one class per
  process meanwhile). This is the most urgent of the open needs: a stall
  takes down serving, where the others only cost time.
- **A subexpression shared within one call.** This is the confit loop's
  ticket T1, in progress.
  - Waiting on it: `Normalizer` l1 and l2 past 16 to 32 features, the max
    norm past 8, and a `Normalizer` serve that is only 3x faster than the
    twin.
  - Compositions (a `Pipeline` of entries) will need it most, since each
    stage's lanes repeat inside the next stage's lanes.
- **An early size refusal.** This is the confit loop's ticket T2, in
  progress. Today a refusal arrives only after Cranelift has spent its
  time: 9 s for a 32-feature l1 `Normalizer`, 55 s for a 48-feature l2
  one. `to_native` pays that before falling back to Python.
- **Build time linear in the lanes read, in the catalog's shape.**
  - After #348, build time is still quadratic here: {{CURVE_SUMMARY}}.
  - `null_when` (which makes a NULL id a NULL struct) multiplies it by
    about 5.
  - Sent to the confit loop on 2026-10-05 with a repro that runs without
    the catalog. #348's own measurement shows near-linear growth for a
    similar shape, so the two shapes differ somewhere.
  - Waiting on it: fixtures and steps past a few hundred lanes.

**Questions for the owner.**
1. **How close a matvec entry must be.** The record is
   `decisions/open/matvec-parity-bound.md`.
   - What waits on it: 19 of the 45 "not yet" transformers. These are
     `PCA`, `IncrementalPCA`, `TruncatedSVD`, `FactorAnalysis`, `FastICA`,
     the two random projections, the four PLS-family transformers,
     `LinearDiscriminantAnalysis`, the `KMeans` family and `Birch`, and the
     `RBFSampler`, `SkewedChi2Sampler` and `PolynomialCountSketch` samplers.
   - Evidence: a left-to-right PCA entry is at most 2.99 eps of each lane's
     term scale from BLAS, but up to 9.9e9 ulps of the result (200 seeds).
   - The loop's proposal is a term-scale bound, K · eps · S per lane.
2. **Where an entry may answer and the twin raises.** The record is
   `decisions/open/tolerated-differences.md`. One item remains: the entry
   may answer where sklearn's input validation raises, as for an infinite
   feature.
3. **Should the Python step densify a sparse output?** This is new, from
   finding 9. The record is `decisions/open/sparse-outputs.md`.
   - The defaults `OneHotEncoder()` and `KBinsDiscretizer()`
     (`encode="onehot"`) both return sparse rows. `PythonTransform` cannot
     serve them; it fails at the first call.
   - If the step densified them, the catalog would serve both natively with
     the dense translations it already has.
   - This is a change to `sql_transform._udf`, outside the catalog.
