# infer_arrow accepts struct row columns: the arrow flatten IS the lane (TASK-114)

Ticket: backlog/tasks/task-114 - infer_arrow-accepts-struct-columns-the-flatten-is-the-lane.md
Predecessor: TASK-132, merged -- static struct lanes carry a structured
path, the dotted name is display only
(packages/confit/docs/specs/2026-08-25-static-struct-lane-path-design.md).
The ticket text predates it: what it calls "the dotted lane name doubles
as the ingest path" is now `in_paths: Vec<Vec<String>>`
(duckdb/mod.rs:1194-1197), and the refusal this spec removes is already
keyed on `p.len() > 1`, not on a dot in a name.

Everything below was measured on 2026-08-25 against pyarrow 25.0.0,
DuckDB 1.5.5 with `PRAGMA disable_optimizer`, and confit built from this
worktree (`uv run maturin develop --release`, BUILD_PROFILE=release).
Every DuckDB refusal cell was run three ways -- `PREPARE p AS <sql>` on
its own connection, a plain execute, and a zero-row table -- and all
three agreed, so every refusal named here is bind-phase. No claim in
this document rests on a `con.execute` that conflates the two.

## Goal

Six acceptance criteria, by name:

- the entry-point-agreement criterion: infer_arrow accepts a struct row
  column and agrees with infer_rows row-for-row on the same data.
- the validity-OR criterion: a NOT NULL child under a nullable parent is
  served through the OR of both validity levels; a null parent must NOT
  leak the child's buffer value.
- the nesting criterion: nested structs work to the same depth the row
  path allows.
- the opacity criterion: a struct column the query never references
  stays opaque and does not block the build, matching the row path's
  rule.
- the no-output-change criterion: output-side struct emission is NOT
  built here; the flattened output is unchanged.
- the bench criterion: the serving bench gains a struct-column scenario,
  so the columnar win over infer_rows on this shape is measured rather
  than assumed.

## Non-goals

- Output-side struct emission. `infer_arrow` keeps emitting flattened
  scalar columns; `arrow::output_schema` and `arrow::emit`
  (duckdb/arrow.rs:485-754) are not touched, and `output_schema` returns
  byte-identical schemas for every query that builds today. The ticket
  raises the emission question separately and this spec does not answer
  it. There is therefore NO user-facing API or format decision in this
  work: the change turns one refusal into a serve and adds no new
  spelling anywhere.
- Pruning unreferenced lanes. Neither entry point does this today:
  measured, a row schema with an unreferenced scalar `unused` refuses
  `Row for table '__THIS__' is missing attribute 'unused'` on the row
  path and `infer_arrow: missing column 'unused'` on the arrow path, and
  an unreferenced struct behaves identically. Making unreferenced lanes
  free is a change to `in_cols` construction that would move both
  entry points at once; it is not this ticket.
- Accepting a PRE-FLATTENED batch. A batch carrying a column literally
  named `st.x` for a declared struct `st` refuses (`missing column
  'st'`), before and after. TASK-132's rule is that a name is not a
  path, and a plain column literally named `a.b` already serves through
  infer_arrow today (measured) -- the two must not collide.
- A struct column as a whole value, `SELECT *` over a struct row table,
  struct join keys. Those refuse today on BOTH entry points and keep
  refusing; they are TASK-125 / TASK-127 territory.
- A struct field whose own NAME contains a dot. `build_fields`
  (duckdb/mod.rs:1305) makes it `StructNode::Opaque`, so it is not a
  lane and ingest never sees it. Same non-goal TASK-132 recorded.
- Multi-chunk struct columns. They get the existing
  `call combine_chunks() on the table first` refusal, unchanged.
- A declared NOT NULL leaf carrying a real child-level NULL under a
  VALID parent. Measured: DuckDB serves NULL, we refuse
  `column 'st.x' is not nullable but a row has None`. That is the
  pre-existing declared-schema contract shared with every plain NOT NULL
  column (`test_none_into_non_nullable_refuses`), not a struct question;
  it is extended to leaves unchanged and is out of scope.

## DuckDB's model, source-pinned (v1.5.5, read-only audit at
   C:\Users\AmirHossein\repos\github.com\duckdb\duckdb, tag v1.5.5,
   commit d8cdaa33fda8df955cc76ef58a280f68f4cd43fa)

THE FOLD HAPPENS AT ARROW INGEST, NOT AT EXTRACT. This is the whole
design, and it is worth reading in that order.

`StructExtractFunction` (`src/function/scalar/struct/struct_extract.cpp`,
lines 12-25) is three statements:

```cpp
auto &children = StructVector::GetEntries(vec);
auto &struct_child = children[info.index];
result.Reference(*struct_child);
```

There is NO parent-validity fold. `st.x` over a NULL `st` is NULL only
because DuckDB maintains the invariant that a struct's child vectors
already carry the parent's NULLs.

That invariant is established where an Arrow array becomes a DuckDB
vector: `ColumnArrowToDuckDB`, `case LogicalTypeId::STRUCT`, in
`src/function/table/arrow_conversion.cpp` lines 1155-1198. For each
child it first copies the child's OWN arrow validity
(`SetValidityMask`, line 1166) and then explicitly ANDs the parent in:

```cpp
if (!struct_validity_mask.AllValid()) {                 // 1168
    auto &child_validity_mark = FlatVector::Validity(child_entry);
    for (idx_t i = 0; i < size; i++) {
        if (!struct_validity_mask.RowIsValid(i)) {
            child_validity_mark.SetInvalid(i);          // 1172
        }
    }
}
```

and then recurses with that mask as the child's `parent_mask`
(line 1190-1191), so an arbitrarily deep struct gets every ancestor
folded in, one level at a time.

OFFSETS COMPOSE. `GetEffectiveOffset`
(src/function/table/arrow_conversion.cpp:29-39) is
`array.offset + parent_offset + chunk_offset`, with the comment
"Parent offset is set in the case of a struct, it applies to all child
arrays". The struct case passes `array.offset` as the child's
`parent_offset` (line 1166, 1191). This matters because our reader gets
the composed offset from pyarrow instead of computing it (measured
below) and must not add it a second time.

BIND-PHASE REFUSALS (all three legs identical -- PREPARE, EXECUTE,
zero-row):

| SQL | DuckDB |
|---|---|
| `SELECT st.x` | serves |
| `SELECT st.nope` | `Binder Error: Could not find key "nope" in struct` |
| `SELECT st` | serves the whole struct |
| `SELECT st.*` | serves the fields |
| `SELECT st.x.y` | `Binder Error: Cannot extract field 'y' from expression "struct_extract(st, 'x')" because it is not a struct, union, map, or json` |

## The measurement matrix

Verdicts: MATCH = same answer or an equivalent refusal; SEV-n = the
severity ladder (1 trap where DuckDB serves, 2 wrong value, 3 serve
where DuckDB refuses, 4 refuse where DuckDB serves); HAZARD = a cell the
DESIGN must not get wrong, with the wrong answer's severity named.

Fixtures:
- F1 `st STRUCT(x BIGINT NOT NULL)`, parent nullable; rows
  `{x:41} / NULL / {x:7}`; SQL `SELECT st.x + 1 AS o FROM __THIS__`.
- F1L the same, built with
  `pa.StructArray.from_arrays([pa.array([41, 999999, 7])], fields=[x],
  mask=[F,T,F])` so the child buffer holds a LOUD value under the null.
- F3 `a STRUCT(b STRUCT(c BIGINT NOT NULL))`, every level nullable; rows
  `{b:{c:1}} / {b:NULL} / NULL`; SQL `SELECT a.b.c * 10 AS o`.
- F7 F1 sliced: `pa.table({...}).slice(3, 4)` over an 8-row struct.
- F-str `st STRUCT(s VARCHAR, b BOOLEAN, i32 INTEGER)` sliced 1..4 with a
  NULL parent inside the slice.

### a. the entry point disagreement (the ticket)

| cell | DuckDB | ours infer_rows | ours infer_arrow | verdict |
|---|---|---|---|---|
| F1 | `[42, None, 8]` | `[42, None, 8]` | `ValueError: infer_arrow requires an all-scalar row schema (struct columns: use infer_rows())` | **SEV-4** |
| F1, NOT NULL parent AND child | `[2, 3]` | `[2, 3]` | same refusal | **SEV-4** |
| F3 | `[10, None, None]` | `[10, None, None]` | same refusal | **SEV-4** |
| depth 6 `d.f0..f5 + 1` | `[6]` | `[6]` | same refusal | **SEV-4** |
| F7 sliced | `[4, 5, 6, 7]` | n/a (row path takes dicts) | same refusal | **SEV-4** |
| F-str sliced, 3 leaves | `[{'s':'bb','b':False,'i':2}, {'s':None,'b':None,'i':None}, {'s':'dd','b':True,'i':4}]`, out schema `string/bool/int32` | identical | same refusal | **SEV-4** |
| `SELECT st.*` over F1 | `[41, None, 7]` | `[41, None, 7]` | same refusal | **SEV-4** |
| F1 empty table (0 rows) | `[]` | n/a | same refusal | **SEV-4** |
| F1 with 2 chunks | `[42, None]` | n/a | same refusal (the all-scalar one fires FIRST, before the chunk check) | SEV-4 |

The refusal is at CALL time, not build time: `DuckDBInferFn(...)`
succeeds for every row above and `infer_arrow` raises. Source:
duckdb/mod.rs:1626-1634.

### b. the validity fold -- what the design must not get wrong

| cell | value | note |
|---|---|---|
| F1L `.field(0).to_pylist()` | `[41, 999999, 7]` | the child array under a null parent, undecorated: `null_count == 0`, `buffers()[0] is None` |
| F1L `flatten()[0].to_pylist()` | `[41, None, 7]` | pyarrow folds the parent mask, `null_count == 1`, NEW validity buffer, SAME data buffer address |
| F1L DuckDB | `[42, None, 8]` | |
| F1L ours infer_rows | `[42, None, 8]` | |
| a `.field()`-without-fold ingest would serve | `[42, 1000000, 8]` | **HAZARD, SEV-2** |
| F3 `a.field(0).field(0).to_pylist()` | `[1, 0, 0]`, `null_count 0` | `.field()` chained folds NOTHING at any level |
| F3 `a.field(0).is_valid()` | `[True, False, True]` | the middle level's own mask does not see the outer null in row 2 |
| F3 `flatten().flatten()` | `[1, None, None]` | correct, i.e. the OR of all three levels |
| F3 explicit AND of ancestors, each read at its OWN offset | `[1, None, None]` | identical to flatten-flatten |
| nested + sliced (outer sliced, middle nulls, inner offset 5) | AND-of-ancestors `[206, None, 208, 209, 210, None]` == flatten-flatten `[206, None, 208, 209, 210, None]` | raw inner values are `[206, 207, 208, 209, 210, 211]` -- the null slots hold real neighbouring values, not zeros |

Two facts make this the top risk in the ticket. First, the buffer under
a null parent is not reliably zero: `Table.from_pylist` happens to leave
0 there, `StructArray.from_arrays` leaves whatever the child array held.
Second, `null_count == 0` on the child is TRUE and correct at the arrow
level -- there is nothing in the child array that signals the problem.
Only the parent knows.

### c. offsets and lengths through the child walk

| cell | measured |
|---|---|
| parent sliced `(3,4)`, child offset 0 | `sl.field(0).offset == 3`, values `[3,4,5,6]`, data buffer address IDENTICAL to the unsliced child |
| child with its own offset 4, parent NOT sliced | `parent.field(0).offset == 4` |
| child offset 4, parent sliced `(2,3)` | `sl.field(0).offset == 6` -- pyarrow COMPOSES (4+2), matching DuckDB's `GetEffectiveOffset` |
| the same through `flatten()` | offset also 6, new validity bitmap indexed at 6, data buffer shared |
| flatten's new validity vs the array offset | bits are read at `offset + i`; with parent offset 1 and child offset 0 the flattened bitmap is byte-identical to the parent's |
| child array LONGER than the parent (3-row struct over a 50-element child) | `len(p.field(0)) == 3`, offset 0 -- pyarrow truncates to the parent's length |
| each ancestor's offset in the nested+sliced case | outer 1, middle 1, inner 6 -- ancestors do NOT share one offset |

Consequence: `RawArray`'s existing `valid(i)` (`bit = self.offset + i`,
duckdb/arrow.rs:33-44) and `data<T>(slot)` (`ptr.add(self.offset)`,
:48-51) are already correct for a struct child obtained from pyarrow, in
both the `.field()` and `flatten()` forms -- as long as each ancestor is
read through its OWN RawArray. Nothing about the buffer reader changes.

### d. the opacity criterion

| cell | ours infer_rows | ours infer_arrow | verdict |
|---|---|---|---|
| unreferenced `ts STRUCT(t TIMESTAMP)` beside `k`, `SELECT k+1` | serves | **serves today** | MATCH, must stay |
| unreferenced `st STRUCT(x BIGINT)` beside `k`, `SELECT k+1`, column PRESENT | serves | refuses (all-scalar) | SEV-4, fixed here |
| the same, struct key ABSENT from the row / column absent from the batch | `Row for table '__THIS__' is missing attribute 'st.x'` | (unreachable today) | after: `infer_arrow: missing column 'st'` -- the row path's rule |
| unreferenced SCALAR `unused` absent | `missing attribute 'unused'` | `infer_arrow: missing column 'unused'` | MATCH today, unchanged |

Read plainly: "stays opaque and does not block the build" means the
all-opaque struct (zero lanes, never looked at) and the servable struct
(lanes, required in the batch exactly as on the row path). The mixed
case falls out of the same rule -- a struct with one servable and one
opaque field contributes ONE lane, and the design walks only that lane's
path, so the opaque sibling is never touched, never flattened, never
type-checked.

### e. things that must not move

| cell | today | after |
|---|---|---|
| plain column literally named `a.b`, `SELECT "a.b" + 1` through infer_arrow | serves `[8]` (DuckDB agrees) | unchanged -- the walk uses the PATH `["a.b"]`, one segment |
| all-scalar schemas, every existing infer_arrow test | serves | unchanged; the hot loop gains one `[].iter().all()` |
| `output_schema` for every query that builds today | flattened scalars | identical |
| `SELECT st` / `SELECT *` over a struct row table | build refuses by name on both entry points | unchanged |
| batch struct child `int32` where the schema declares `int64` | masked by the all-scalar refusal | `infer_arrow: column 'st.x' is int32, the schema declares int64 -- cast first` (the top-level rule, extended) |

### f. cost, and the columnar win (n = rows, K = 20 double leaves)

Child-array access, median of 200 (constant in n -- all three are
Python-object cost, not data cost):

| n | `.field(i)` x K | `flatten()` x 1 | `flatten()` per lane (x K) |
|---|---|---|---|
| 64 | 7,300 ns | 12,000 ns | 239,400 ns |
| 1024 | 7,100 ns | 11,600 ns | 240,400 ns |
| 8192 | 7,400 ns | 12,100 ns | 241,800 ns |

`.field()` allocates no buffer at all (address-identical child data);
`flatten()` allocates one fresh validity bitmap PER CHILD PER CALL, so
calling it once per lane is quadratic in the struct's width.

The columnar win on the struct shape. Direct measurement is impossible
before the feature exists, so this is the honest proxy: the SAME lane
set and the SAME program, `infer_rows` over the struct schema against
`infer_arrow` over the equivalent flat schema (20 f64 leaves, `x*2+1`
per leaf, cranelift both sides), median of 60:

| n | infer_rows (flat) | infer_rows (struct) | infer_arrow (flat) | struct-rows / arrow |
|---|---|---|---|---|
| 1 | 1,500 ns | 1,800 ns | 187,300 ns | 0.01x |
| 64 | 68,000 ns | 83,400 ns | 116,100 ns | 0.7x |
| 1024 | 1,100,300 ns | 1,337,400 ns | 264,200 ns | **5.1x** |
| 8192 | 11,581,900 ns | 14,372,200 ns | 2,985,800 ns | **4.8x** |

Two readings. The win at n >= 1024 is real and is slightly LARGER on the
struct shape than on the flat one, because the row path pays an extra
dict walk per leaf (1.337 ms vs 1.100 ms at n=1024, +22%). And the
crossover is unchanged: arrow still loses below ~a few hundred rows, so
the bench must report all four n and the spec must not claim a
universal win. This is the number the bench criterion exists to replace
with a measured one.

## Design

Three edits. Nothing in bind, lowering, either backend, or emit moves.

### D1. `ingest` takes the lane paths and walks them

`ingest` (duckdb/arrow.rs:157) gains `in_paths: &[Vec<String>]`. Its one
caller (duckdb/mod.rs:1635) already has them. Per lane, instead of
`column(batch, &c.name, "infer_arrow")`:

```rust
/// The leaf array for one lane, plus every struct ancestor along its
/// path. DuckDB folds the parent's mask into each child at arrow
/// ingest (arrow_conversion.cpp:1168-1175) and struct_extract itself
/// does not (struct_extract.cpp:23) -- so the fold belongs HERE.
fn walk_lane<'py>(
    batch: &Bound<'py, PyAny>,
    path: &[String],
    display: &str,
) -> PyResult<(Bound<'py, PyAny>, Vec<RawArray<'py>>)> {
    let mut arr = column(batch, &path[0], "infer_arrow")?;
    let mut parents = Vec::new();
    for seg in &path[1..] {
        let ty = arr.getattr("type")?;
        let idx: i64 = match ty.call_method1("get_field_index", (seg.as_str(),)) {
            Ok(v) => v.extract()?,
            // not a struct type: no such method
            Err(_) => return Err(err(format!(
                "infer_arrow: column '{display}': '{}' is {}, the schema \
                 declares a struct -- cast first",
                path[0], ty.str()?
            ))),
        };
        if idx < 0 {
            return Err(err(format!(
                "infer_arrow: column '{display}': the batch's struct '{}' \
                 has no field '{seg}'",
                path[0]
            )));
        }
        let child = arr.call_method1("field", (idx,))?;
        parents.push(raw_array(arr)?);
        arr = child;
    }
    Ok((arr, parents))
}
```

`column()` is reused unchanged, so a struct column with two chunks gets
the existing `call combine_chunks() on the table first` message and an
absent struct gets the existing `missing column` message, both for free.
`.field(idx)` is chosen over `.field(name)` because pyarrow raises
`KeyError` for a missing AND for an AMBIGUOUS name; `get_field_index`
returns -1 for both, and one refusal covers both (a duplicate-named
struct field is unreachable through the row path anyway -- pyarrow
itself cannot `to_pylist` one).

### D2. one closure ORs the ancestors in

Inside `ingest`'s per-lane block, after `let raw = raw_array(arr)?;`:

```rust
// The null lane is the OR of every level: a NOT NULL child under a
// nullable parent has no validity buffer of its own, and its data
// buffer under a null parent holds an arbitrary live value.
let valid_at = |i: usize| parents.iter().all(|p| p.valid(i)) && raw.valid(i);
```

The four value loops (`I8|I16|I32|I64`, `F64`, `I1`, `Str`) swap
`raw.valid(i)` for `valid_at(i)` -- four one-token edits. Everything
else in those loops (`raw.data::<T>(1)`, `raw.bufs[1]`, `str_bytes(&raw)`,
`raw.offset`) reads the LEAF and is untouched, which is correct: the
leaf's own offset is the composed one (matrix c). `null_seen` and the
existing `null_seen && !c.ty.nullable` refusal then work on the folded
validity, which is exactly right -- a leaf lane's `Col.ty.nullable` is
already `parent_nullable || own_nullable` (duckdb/mod.rs:1317-1323).

Cost on the all-scalar path: `parents` is `Vec::new()`, which does not
allocate, and `[].iter().all(..)` is a length compare. The dtype check,
the row-count check and the `Batch` construction are untouched.

Ancestors are stored as `RawArray`, not as validity `Vec<bool>`, on
purpose: each ancestor carries its OWN offset (measured: outer 1,
middle 1, inner 6 in one nested slice), and `RawArray::valid` already
reads a bitmap at an offset correctly.

### D3. the refusal is deleted

duckdb/mod.rs:1626-1634 -- the `in_paths.iter().any(|p| p.len() > 1)`
block and its message -- goes away. `in_paths` stops being unused in
`infer_arrow` and becomes its argument to `ingest`. That is the entire
`mod.rs` diff.

### Rejected alternative

Flatten the whole table instead: call `pa.Table.flatten()` repeatedly
until no struct column remains and let the existing by-name ingest find
the `parent.child` columns pyarrow names for it. It is two lines, it is
correct about validity for free, and it is wrong three ways. It
re-introduces exactly the name-as-path encoding TASK-132 deleted, so a
row schema with a struct `st{x}` and a plain sibling column literally
named `st.x` -- which serves today, measured -- becomes an ambiguous
lookup. It flattens EVERY struct column and EVERY child, including the
unreferenced ones the opacity criterion is about, allocating a validity
bitmap for each. And it costs 12 us per flatten level against 7 us for
all twenty `.field()` calls, per batch, on a boundary whose entire
reason to exist is that it does not allocate per value. A cached
flatten-once-per-struct-column would fix the cost but needs a per-column
cache keyed by path prefix, which is more machinery than the closure it
replaces, and still cannot answer the `a.b` collision.

## Behavior flips, each severity-classified

Every flip is a bug fix and gets a live-oracle pin.

1. **SEV-4 -> MATCH.** `infer_arrow` serves a struct row column: flat,
   nested, sliced, empty, string/bool/narrow leaves, `st.*` expansion.
   The two entry points stop disagreeing. (D1+D3)
2. **HAZARD SEV-2 avoided, pinned.** A null parent nulls the lane
   instead of serving the child buffer's value. The pin uses a fixture
   whose buffer holds 999999 under the null, so the test fails loudly
   if the fold is ever dropped, rather than passing on a lucky zero.
   (D2)
3. **HAZARD SEV-2 avoided, pinned.** The same at every level of a
   nested struct, and under a slice where the null slot's raw value is a
   real neighbouring row's. (D2)
4. **SEV-4 -> MATCH.** An unreferenced struct column with servable
   leaves no longer blocks `infer_arrow`; it is required in the batch on
   exactly the terms the row path requires the attribute.
5. **MSG only.** A struct-shaped batch that does not match the declared
   schema now refuses with the specific reason (`has no field 'x'`,
   `is int32 ... cast first`, `is int64, the schema declares a struct`)
   instead of the blanket all-scalar sentence.
6. **No flip, stated for the record.** All-scalar schemas, the plain
   `a.b` column, `output_schema`, the whole-struct and star refusals,
   the multi-chunk refusal, and the NOT NULL-leaf-with-a-real-null
   refusal all keep their current behavior and their current text. The
   implementation must not touch them.

## Display and message notes

TASK-132's display rule holds and is not extended: a path renders dotted
in ERROR TEXT only, and the dotted spelling comes from `Col.name`, which
`build_fields` already builds for display (duckdb/mod.rs:1319). D1 and
D2 construct no new dotted string -- `walk_lane` receives `display` as
`&c.name` and passes it through.

Message shapes, all reusing existing spellings:

| condition | text |
|---|---|
| struct column absent from the batch | `infer_arrow: missing column 'st'` (existing `column()`) |
| struct column has >1 chunk | `infer_arrow: column 'st' has 2 chunks - call combine_chunks() on the table first` (existing) |
| the batch's `st` is not a struct | `infer_arrow: column 'st.x': 'st' is int64, the schema declares a struct -- cast first` |
| the batch's `st` has no field `x` | `infer_arrow: column 'st.x': the batch's struct 'st' has no field 'x'` |
| leaf dtype mismatch | `infer_arrow: column 'st.x' is int32, the schema declares int64 -- cast first` (existing text, leaf name) |
| leaf NULL into a non-nullable lane | `column 'st.x' is not nullable but the batch has NULLs` (existing text, leaf name) |

The deleted message (`infer_arrow requires an all-scalar row schema
(struct columns: use infer_rows())`) is asserted on by two tests, named
in the test plan; both flip.

### Fuzzer

`packages/confit/fuzz/oracle.py` carries an explicit TASK-114 escape
hatch: `rows_only` (lines 571-580) routes any struct-bearing case
through `infer_rows` and tags it, and `_extra_legs` (lines 718-731)

plan, stronger than any hand-written pin.
