# The lossy join key rides as a shadow value lane (TASK-120)

Predecessor: TASK-115 (`test_projected_static_key_takes_the_static_columns_width`)
-- a projected static key takes the STATIC column's own declared width.
Between two integer widths that is a pure re-declaration and it is exact,
because DuckDB compares across widths NUMERICALLY, so a match already proves
the value fits both. This document covers the one pairing where no such
re-declaration exists, and which TASK-115 therefore left refusing by name: a
DOUBLE probe against an INTEGER static key.

Everything below was measured on 2026-08-25 against DuckDB 1.5.5 with
`PRAGMA disable_optimizer`, and against confit built release from
packages/confit (`uv run maturin develop --release`). Our refusals are
labelled by the phase that raises them: `bind` for a prepare-time
`PrepareError`, `build` for a static-data error raised while the probe table
is materialised.

## Goal

The four TASK-120 acceptance criteria, by name:

- The serve-the-real-value criterion: "a projected integer key column joined
  against a DOUBLE probe serves the STATIC column's real value at its
  declared type, not a reconstruction."
- The read-the-column criterion: "the fix reads the real column (materialise
  the key as a probe VALUE lane when it is projected) rather than converting
  the double back -- the conversion is the unsound part."
- The multiplicity-measured-first criterion: "multiplicity is measured first:
  two int64 build rows that collide on one double are one bucket for us;
  check what DuckDB emits for both shape='map' and shape='many' before
  choosing the fix."
- The test-rewrite criterion (the Test plan below spells it AC #4):
  "`test_a_double_probe_against_an_integer_key_refuses_to_project_it` in
  test_integer_widths.py is rewritten to assert the served answer."

Two of the four come back from the measurement changed, and both changes are
load-bearing:

- The multiplicity premise is FALSE. Two colliding build rows are NOT one
  bucket for us: under shape='many' they are two entries and they fan out
  exactly like DuckDB, and under the unique shapes (default/'map') the build
  REFUSES with `duplicate map key`, the same refusal genuine i64 duplicates
  get. Nothing collapses silently, so the ROWS never diverged and the fix
  needs no multiplicity change at all. Only the PROJECTION was ever wrong
  (matrix c).
- The read-the-column criterion says "when it is projected". The lane list is
  fixed when the JOIN is bound, before any SELECT list exists, so the branch
  emits the shadow lane for every LOSSY pairing rather than gating it on
  projection (D2). That is the only point in the pipeline where the decision
  can be made, and it costs one probe lane per lossy key column.

## Non-goals

- Multiplicity and the shape contract. A static whose keys collide still
  refuses under the unique shapes and still fans out under shape='many'; this
  branch changes neither, because the measurement showed neither is wrong.
- The USING merge rule. A USING key still merges into the LEFT (probe)
  occurrence, so bare `c0` and `*` still serve the probe's DOUBLE. The shadow
  lane must stay invisible to that rule, not amend it (D5).
- The sound pairings. An integer probe against a DOUBLE static key promotes
  the probe and is exact; two integer widths re-declare (TASK-115). Neither
  grows a lane, and neither changes here.
- Struct-leaf join keys. `static_col_of` skips leaf lanes (TASK-132), so a
  struct leaf never becomes a key column: `ON k = s.w.mean` falls to the
  residual and the leaf stays an ordinary value lane. Measured: it already
  serves the right i64. It is the read-the-column shape, already proven.
- Any API surface change, new struct field, `StaticSpec` shape change, or
  lowering edit. The whole branch is inside `specializer/frontend.rs`.

## Why DuckDB can serve it: the key travels twice (v1.5.5 source)

The equality binds at DOUBLE, and the INTEGER side is the one that gets cast:

- `bind_comparison_expression.cpp:79-80` takes an equality's two types
  through `ForceMaxLogicalType`, which lands in
  `LogicalType::CombineUnequalTypes` (`types.cpp:926-941`).
- The tie-break is the implicit-cast cost table: `ImplicitCastBigint(DOUBLE)
  = 104`, `ImplicitCastDouble(BIGINT) = -1` (`cast_rules.cpp`). BIGINT ->
  DOUBLE is allowed, DOUBLE -> BIGINT is not, so the comparison binds at
  DOUBLE.
- `bind_comparison_expression.cpp:181-184` adds that cast to the
  comparison's CHILDREN only. Nothing else in the plan is retyped.

So DuckDB's comparison is in double space too -- it has exactly the same
information we do -- and it still projects the right i64. The reason is the
hash join:

- `physical_hash_join.cpp:45-53`: a build column is reused from the
  CONDITION slot only when the condition's child is a bare `BOUND_REF`.
  Under a cast it is not.
- So `s.c0` is collected into the PAYLOAD as well (`:87-101`), at BIGINT.

DuckDB carries the key TWICE: once cast to DOUBLE for the comparison, once at
its own declared width in the payload. That is the design this branch
mirrors, and it is why no amount of cleverness on the comparison side can
substitute -- the comparison genuinely does not name one i64.

## The matrix

Fixture: static `s(c0 <int width>, v BIGINT)`, row `__THIS__(k DOUBLE)`,
`JOIN s ON k = s.c0`. Constants:

```
_P53   = 9007199254740992   # 2**53
_P53_1 = 9007199254740993   # 2**53+1, float(_P53_1) == float(_P53)
```

The probe value is `float(_P53)` = 9007199254740992.0 unless a cell says
otherwise. `ONE` = static rows `{(_P53_1, 7)}`; `PAIR` = `{(_P53, 70),
(_P53_1, 71)}`.

Verdicts: MATCH = same answer or an equivalent refusal; SEV-n = the severity
ladder (2 wrong value, 3 serve where DuckDB refuses, 4 refuse where DuckDB
serves); CONTRACT = both engines are self-consistent and our refusal is the
documented shape contract, not a divergence in rows.

### a. the projected key, ONE static row -- no multiplicity involved

| cell | DuckDB | ours (before) | verdict |
|---|---|---|---|
| `SELECT s.c0`, static ONE | 9007199254740993, BIGINT | bind: `projecting join key column 's.c0': it is declared i64 but the join compares it as f64, and the original value is not recoverable from the comparison` | SEV-4 |
| the same cell, had the key been reconstructed from the probe | 9007199254740993 | 9007199254740992 | **SEV-2** |
| `SELECT s.v` (key not projected) | 7 | 7 | MATCH |

The second row is the whole argument. It is a single build row, so no
collision and no multiplicity question arises; a re-declaration of the
probe's double under the column's name is simply a WRONG VALUE. That kills
the re-declaration alternative on its own, before any fan-out reasoning. The
third row is why the ticket says only the PROJECTION refuses: the join
itself, and every other column, were always fine.

### b. the same value, every other spelling (static ONE)

| cell | DuckDB | ours (before) | verdict |
|---|---|---|---|
| `SELECT *` | serves | same bind refusal | SEV-4 |
| `SELECT c0` (bare) | serves | same bind refusal | SEV-4 |
| `SELECT s.c0 + 1` | serves | same bind refusal | SEV-4 |
| `SELECT s.c0 = 9007199254740993` | serves | same bind refusal | SEV-4 |

Every one of these resolves the same column spelling, so they all funnel
through `key_lane`. They flip together or not at all, which is why the fix
has to sit in the lane, not in the projection site.

### c. multiplicity, MEASURED FIRST (static PAIR, `SELECT s.v`)

| cell | DuckDB | ours (before) | verdict |
|---|---|---|---|
| shape='many' | 2 rows, `{71, 70}` | 2 rows, `{70, 71}` | MATCH (sorted-multiset order contract, `test_duckdb_stageb_many.py`) |
| shape='filter' (default) | 2 rows | build: `static data mismatch: @0: duplicate map key` | CONTRACT |
| shape='map' | 2 rows | same build refusal | CONTRACT |
| control: genuine duplicate i64 keys `{5, 5}`, unique shapes | n/a | the identical refusal | the refusal is the shape contract, not a collision collapse |

This is the criterion's answer, and it is the opposite of the premise. There
is no silent bucket: 'many' fans both rows out with their own key values, and
the unique shapes refuse the static outright, exactly as they would for two
literally equal i64 keys. So the fix needs no multiplicity change, and the
row SETS never diverged -- only the value projected for the key column did.

### d. USING merges the key (row column `c0 DOUBLE`, static `c0 BIGINT` = ONE)

| cell | DuckDB | ours (before) | verdict |
|---|---|---|---|
| `SELECT c0` | 9007199254740992.0, DOUBLE (the probe occurrence) | same | MATCH |
| `SELECT *` | one merged `c0` at DOUBLE 9007199254740992.0 | same | MATCH |
| `SELECT s.c0` | 9007199254740993, BIGINT | bind refusal (as in a) | SEV-4 |

Three cells that must NOT move. Under USING the merged name belongs to the
probe and keeps the probe's double; only the explicit static spelling reaches
the i64. A shadow value lane that leaked into name resolution would break the
first two while fixing the third, which is what D5 exists to prevent.

### e. the width sweep (static `c0` = 5 at each width, probe 5.0, `SELECT s.c0`)

| static width | DuckDB | ours (before) | verdict |
|---|---|---|---|
| TINYINT (int8) | serves 5, out int8 | bind: `cannot join f64 with i8 (ON 'c0')` -- the WHOLE join | SEV-4 |
| SMALLINT (int16) | serves 5, out int16 | bind: `cannot join f64 with i16 (ON 'c0')` -- the WHOLE join | SEV-4 |
| INTEGER (int32) | serves 5, out int32 | bind: `cannot join f64 with i32 (ON 'c0')` -- the WHOLE join | SEV-4 |
| BIGINT (int64) | serves 5, out int64 | the join binds; only the key PROJECTION refuses | SEV-4 |

### f. cells that already agree, and must survive

| cell | DuckDB | ours (before) | verdict |
|---|---|---|---|
| integer probe vs DOUBLE static key | serves | serves (probe promotes to f64) | MATCH |
| `ON k = s.w.mean` (struct-leaf key) | serves the i64 | serves the i64 | MATCH |

The struct-leaf row is worth reading twice: `static_col_of` skips leaf lanes,
so that conjunct never becomes a key at all -- it falls to the residual and
the leaf stays an ordinary VALUE lane, which serves its real value at its
real width. The shape this branch adopts is already in the engine and already
proven; TASK-120 gives the same treatment to a column that IS a key.

## Scope: the ticket names one width, the arm has four

The ticket's example is BIGINT, where the join binds and only the projection
refuses. Row (e) says the hole is bigger: `promote_key`'s static-side arm was
`(Ty::F64, Ty::I64)` alone, so a TINYINT, SMALLINT or INTEGER static key
refused the ENTIRE join against a DOUBLE probe -- a severity 4 on queries
DuckDB serves without complaint, and a strictly larger blast radius than the
projection bug the ticket describes.

It is the same arm and the same fix: DuckDB compares all four widths against
a DOUBLE in double space (the source above makes no width distinction), so
all four are lossy in exactly the same way and all four need the shadow lane.
Fixing the projection for int64 while leaving the other three unjoinable
would ship a fix that the ticket's own test parametrisation cannot express.
So the branch covers all four, and the width sweep is a parametrised pin
rather than a single case.

## Design

Mirror DuckDB: carry the key twice. Everything is in
`packages/confit/src/specializer/frontend.rs`.

### D1. `key_is_lossy` -- name the pairing once (:1425-1433)

```rust
fn key_is_lossy(key_ty: Ty, col_ty: Ty) -> bool {
    key_ty == Ty::F64 && col_ty.is_int()
}
```

`key_ty` is the key expression's type AFTER `promote_key`, which is what the
map is built on. So an integer probe against a DOUBLE static column reads
F64 vs F64 here and is NOT lossy -- that pairing promotes the PROBE and stays
exact. Only the direction where the STATIC side is converted qualifies.

### D2. the shadow value lane (`val_cols_for`, :1435-1447)

```rust
fn val_cols_for(st: &StaticTable, key_cols: &[u32], keys: &[SExpr]) -> Vec<u32> {
    let mut val: Vec<u32> = (0..st.cols.len() as u32)
        .filter(|c| !key_cols.contains(c))
        .collect();
    for (kp, &c) in key_cols.iter().enumerate() {
        if key_is_lossy(keys[kp].ty, st.cols[c as usize].ty.ty) {
            val.push(c);
        }
    }
    val
}
```

Called at both join-binding sites: the explicit JOIN arm (:891, covering ON,
USING and NATURAL alike) and the comma-join arm (:1055). The shadow is
APPENDED after the ordinary value lanes, so no existing lane position shifts
-- which is what lets the rest of the pipeline stay untouched: `StaticSpec`
maps every `val_cols` entry through `plan::lane_paths` (specializer/mod.rs),
so the shadow is simply the same column path listed a second time, and the
materialiser reads that path again per build row (duckdb/mod.rs:778). No new
struct field, no new spec field, no lowering edit.

The lane is unconditional for a lossy pairing rather than gated on
projection: `val_cols` is fixed while the FROM clause is bound, before the
SELECT list is seen. The cost is one extra probe lane per lossy key column,
and only for a pairing that today either refuses the projection or refuses
the whole join.

### D3. `key_lane` serves the lane instead of reconstructing (:3439-3462)

```rust
if key_is_lossy(key.ty, col.ty.ty) {
    let pos = sj
        .val_cols
        .iter()
        .position(|&v| v == ci)
        .expect("a lossy key column has a shadow value lane");
    return Ok(self.static_lane(j, pos));
}
```

An early return, ahead of the type match. Three consequences, all measured
requirements:

- the served TYPE is the static column's own declaration (`static_lane` takes
  it from `sj.table.cols`), so the width sweep keeps int8 as int8;
- the served VALUE is the build row's, never the probe's;
- a LEFT miss is NULL with no CASE wrapper, because `static_lane` is already
  nullable when `sj.kind == JoinKind::Left` -- the ordinary value-lane rule
  carries the miss.

The old refusing arm keeps its message for every pairing that is still
neither equal, nor int/int, nor lossy.

### D4. `promote_key` widens to every integer width (:1403-1420)

```rust
(Ty::F64, b) if b.is_int() => Ok(key),
```

was `(Ty::F64, Ty::I64)`. The map key type stays F64 and the build side is
still converted while the probe table is built; the only change is that
int8/int16/int32 statics are now admitted, matching DuckDB, and their real
values are recoverable because D2 gave them a lane.

### D5. the shadow lane is not a binding -- three guards and one reorder

```rust
fn is_shadow_lane(sj: &ScopeJoin, pos: usize) -> bool {
    sj.key_cols.contains(&sj.val_cols[pos])
}
```

A no-op on every join without a lossy key, because `key_cols` and `val_cols`
are otherwise disjoint by construction. The three guards are one line each,
alongside the existing `is_leaf_lane` skip:

- `head_hits_in_join` (:1141-1150) -- the ambiguity COUNTER behind
  `bare_col_with_fields` and `binds_in_join`. Unguarded, a lossy key head
  counts two bindings and every reference to it refuses as ambiguous.
- `Binder::column` (:3848-3850) -- unqualified resolution. Unguarded, an ON
  join would produce two hits (`ambiguous column`), and a USING join -- where
  the key arm is deliberately suppressed -- would answer the bare name with
  the static i64 where DuckDB gives the merged probe DOUBLE.
- `Binder::qualified` (:4005-4009) -- `s.c0` falls through the value scan to
  the key arm, so the spelling keeps routing through `key_lane`.

The reorder is in star expansion (`expand_star_lanes`, :2303-2316): the
per-column dispatch now tests KEY membership first and only then looks for a
value lane. A lossy key column is in both lists, and taking the value branch
would emit it as an ordinary column -- unmerging a USING key and adding a
phantom column DuckDB never produces. Column ORDER is unchanged; the loop
still walks `sj.table.star` in declared order.

All four land together: they are what keeps `*`, USING and bare names correct
the moment `key_lane` starts reading the shadow.

## Behavior flips

Each is a bug fix; each gets a live-oracle pin.

1. SEV-4 -> MATCH. `SELECT s.c0` over a DOUBLE-probe / integer-key join
   serves the static column's real value at its declared width. The i64 the
   probe's double cannot name (9007199254740993 under a 9007199254740992.0
   probe) is served, and the value a reconstruction would have produced is
   pinned as wrong. (D2 + D3)
2. SEV-4 -> MATCH. A TINYINT, SMALLINT or INTEGER static key joins against a
   DOUBLE probe at all, and its projection keeps int8/int16/int32. (D4)
3. SEV-4 -> MATCH. Every other consumer of that spelling flips with it:
   `SELECT *`, the bare name, `s.c0 + 1`, a comparison against the literal
   only the i64 can equal, and an ON residual over the key. (D3 + D5)
4. No flip, stated for the record: USING still merges (bare `c0` and `*`
   still give the probe's DOUBLE 9007199254740992.0), shape='many' still fans
   colliding keys out, the unique shapes still refuse `duplicate map key`,
   the integer-probe-vs-DOUBLE-static pairing and the TASK-115 int/int
   re-declaration are untouched, and a struct-leaf key still serves through
   its own value lane. The implementation must not move any of them.

One invariant carries the whole design: for a lossy pairing the map key stays
what `promote_key` made it, a double, and the static column's real value
lives in the shadow lane alone -- every spelling that names that column is
served through it, never in the map key.

## Sequencing

One branch (task-120), commits by class, each red first:

1. `key_is_lossy` + `val_cols_for` + the two call sites, with
   `key_lane` still refusing -- everything stays green, only the IR
   for an already-serving lossy join grows a lane.
2. `key_lane` reads the shadow lane; the three resolution guards land
   in the same commit (they are what keeps USING and bare names
   correct). Flips 1 and 3 pinned.
3. `promote_key` widens to every integer width. Flip 2 pinned.
4. Test rewrite (AC #4) and the survive list re-run.

Half a day. No API surface changes, no new struct fields, no lowering
edits.
