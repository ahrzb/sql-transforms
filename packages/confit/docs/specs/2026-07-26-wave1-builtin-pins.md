# Builtin pins: predicates, math, string search, LIKE

DuckDB 1.5.5. Every claim was measured through the vectorized path (table
columns, not literals); the full pin tables (300+ rows incl. exact reprs,
result types, and error heads) are the JSON files in `pins-wave1/`. Where
the constant-fold path diverges it is noted. Nothing here is inferred from
documentation.

## Frontend desugars (no dedicated IR)

- `x BETWEEN lo AND hi` → `(x >= lo) AND (x <= hi)`; `NOT BETWEEN` →
  `NOT(...)`. Kleene AND over `duck_fcmp` reproduces every pinned row,
  including `(5, NULL, 4) → FALSE` (NULL AND FALSE) and NaN-above-inf
  ordering. There is no empty-range special case, and none may be added
  (short-circuiting the NULL/FALSE interplay diverges).
- `x IN (a, b, …)` → Kleene OR-chain of equalities; `NOT IN` → `NOT(...)`.
  `1 IN (1,NULL)` = TRUE, `3 IN (1,NULL)` = NULL. Type unification is
  WHOLE-EXPRESSION (one common type across x and every element; a single
  DOUBLE drags the list to DOUBLE). `x IN ()` is a parse error in DuckDB.
- `power(x,y)` / `pow(x,y)` → one pow op. In DuckDB `^` and `**` are also
  pow (not xor); unary minus binds TIGHTER (`-2^2 = +4.0`); they are
  LEFT-associative (`2^3^2 = 64`). confit refuses the `^` operator:
  sqlparser parses it below `*`, DuckDB above.
- `pi()` → the f64 literal 0x400921FB54442D18.
- Aliases → one op each: instr = strpos = 2-arg `position(haystack,
  needle)`; SQL `position(n IN s)` is needle-first; prefix = starts_with,
  suffix = ends_with; len = char_length = character_length = length; `^@`
  = starts_with.
- `least/greatest(n-ary)` → left fold of the binary op (first-arg-wins on
  ties makes the fold exact).

## Math

Unary (DOUBLE → DOUBLE; integer inputs cast to DOUBLE first; VARCHAR/
BOOLEAN columns are binder errors — no implicit cast):

- `ln`, `log2`, `log10`: TRAP on x ≤ 0 — "cannot take logarithm of zero" /
  "cannot take logarithm of a negative number" (exact heads in pins); -0.0
  hits the ZERO check first. NaN (either sign) passes through to libm-NaN
  (comparison-based guard, not is_finite). NULL pre-empts every domain
  check. Otherwise bit-exact platform libm.
- `exp`: TOTAL. exp(1000) = inf, exp(-inf) = +0.0, underflow passes
  through denormals (exp(-745) = 5e-324).
- `sqrt`: TRAP on any negative incl. -inf ("cannot take square root of a
  negative number"); sqrt(-0.0) = -0.0.
- `cbrt`: TOTAL; cbrt(-8) = -2.0 exactly (not pow(x,1/3), which is NaN).
  DuckDB's own wheels disagree by one ulp across platforms (Windows wheel
  == Rust/ucrt bit-exact; the Linux wheel's std::cbrt returns e.g.
  3.0000000000000004 for cbrt(27)). confit uses Rust cbrt; oracle parity
  for cbrt is ≤ 1 ulp, not repr-exact — the only such exception.
- `sin`, `cos`, `tan`: TRAP on ±inf ("Out of Range Error: input value inf
  is out of range for numeric function"); NaN passes through BIT-EXACTLY
  (payload and sign preserved — check is_nan() before calling libm);
  finite inputs bit-match platform libm incl. 1e300. tan(pi()/2) is finite
  1.633…e16.
- `floor`, `ceil`, `trunc`, `round`: Rust `f64::floor/ceil/trunc/round`
  are bit-exact (round is half-AWAY-from-zero, incl. 0.49999999999999994 →
  0.0). floor/ceil have NO integer overloads (int → lossy DOUBLE);
  single-arg trunc/round on integers are identity.

Binary:

- `log(b, x)`: EXACTLY log10(x)/log10(b) — not an ln-ratio or log2-ratio.
  Base is domain-checked BEFORE x; base == 1 has a dedicated error
  (DuckDB's typo verbatim in pins); the sign of zero leaks from the
  division (log(0.5, 1.0) = -0.0).
- `pow(x, y)`: TOTAL, pure IEEE: pow(NaN,0) = 1, pow(1,NaN) = 1,
  pow(0,-1) = inf, negative^fractional = NaN, overflow = inf. Result always
  DOUBLE (no integer pow, no overflow trap).
- `least/greatest` (binary): NULL-IGNORING (NULL only if both are); ties
  return the FIRST argument (pinned via -0.0 vs 0.0); NaN sorts above +inf
  (greatest(x, NaN) = NaN).
- `round(x, n)` / `trunc(x, n)`:
  - round(x, n<0): NaN/±inf → +0.0; n ≤ -309 → 0.0 for every finite x.
  - trunc(x, n<0) on non-finite x returns the INPUT (differs from round).
  - Integer round(int, n<0) WRAPS at i64 (round(i64::MAX,-2) =
    -9223372036854775700); |n| ≥ 19 collapses to 0. Never errors.
  - The DOUBLE scale factor is DuckDB's own std::pow(10,n), which is NOT
    correctly rounded (1 ulp off strtod at n=23). confit uses an
    oracle-extracted pow10 table (n ∈ [-323, 308], `exec/pow10.rs`,
    generated by `scripts/gen_pow10.py`).
  - DuckDB does not bind round(DOUBLE, BIGINT-column) — digits must be
    INTEGER; constant integer digits bind.

## String search

All TOTAL and NULL-strict in every argument (validity = AND of input
validities):

- `instr`/`strpos`/`position`: 1-based CODEPOINT index (not bytes, not
  graphemes), 0 = not found, empty needle → 1 (matches even in '').
- `contains`, `starts_with`, `ends_with`: empty needle → TRUE. Byte-wise
  comparison (no normalization, no case folding).
- `length` counts codepoints; `strlen` counts UTF-8 bytes.

## Catalogue facts

- `log1p`/`expm1` and `truncate` do not exist in DuckDB 1.5.5 (catalog
  error).
- `contains(numeric, …)` etc. have no implicit numeric→VARCHAR cast
  (binder error).
- `'2^-2'` is a bind-time error in DuckDB (the lexer eats `^-`).

## Evaluation order and literals

- WHERE filters and untaken CASE branches prevent evaluation in DuckDB
  (pinned); confit evaluates the projection only after the filter branch.
  A domain-violating row that IS evaluated aborts the whole call in both.
- Bare SQL float literals are DECIMAL in DuckDB (no signed zero; exact
  comparisons against BIGINT); pins use `'…'::DOUBLE` or columns. confit
  types decimal literals as DOUBLE.
- Literal vs vectorized: no divergences in the string-search, trig, log,
  and pow families; DECIMAL-literal round differs by design (confit follows
  the DOUBLE column path).

## LIKE / ILIKE (`pins-wave1/pins_like.json`)

Byte-based matcher, codepoint `_`, no normalization; backslash is a LITERAL
(no implicit escape, unlike Postgres); ESCAPE takes any single BYTE (a
2-byte codepoint errors), doubled = literal, the escape char never matches
itself unescaped, ESCAPE '' = none, ESCAPE NULL = NULL. The dangling-escape
error is DATA-DEPENDENT per row (string exhausted → plain false; bytes
remaining when the matcher examines it → error), reproduced by
leftmost-first backtracking. ILIKE = fold both sides with the measured
simple casemap, then LIKE (exhaustive all-codepoint sweep, zero
exceptions).

DuckDB-side caveats: (1) a stats-dependent ASCII kernel whose only
divergence surface is U+212A/U+0130 in patterns; (2) the generic kernel's
fold NUL-truncates inconsistently, so a NUL-containing row's ILIKE result
depends on SIBLING rows. confit is NUL-transparent; the one affected
corpus case is listed in `_KNOWN_DIVERGENT_SOURCES`
(`tests/test_corpus_replay.py`).

DuckDB's column-pattern LIKE is naive-recursive (23s on one pathological
row); confit's is the O(n·m) two-pointer restart with identical booleans
and error rows.

SIMILAR TO is not a LIKE variant: DuckDB binds it to `regexp_full_match`
on the raw pattern — see `2026-07-27-waveB-regexp-pins.md`.
