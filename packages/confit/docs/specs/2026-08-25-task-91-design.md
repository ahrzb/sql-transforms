# Serving DECIMAL statics exactly (TASK-91)

Ticket: backlog/tasks/task-91 - Serve-DECIMAL-statics-exactly.md.
Extends packages/confit/docs/specs/2026-08-11-duckdb-type-lattice-design.md
(the m-8 type lattice); contradicts nothing in it. That spec's phase 1
("decimal static ingest: exact-or-refuse") shipped as TASK-90 and is what
this task retires; its phase 4 named the i128 lane as the upgrade path.
This spec is that upgrade, restricted to the decimal half: the lane lands,
HUGEINT the frontend type does not, decimal arithmetic does not.

Measurements below are live optimizer-off DuckDB 1.5.5 / pyarrow 25.0.0 on
2026-08-25, taken against the engine built from 7138d0b. DuckDB semantics
are cited to the pinned source checkout, not to memory.

## Goal

A DECIMAL static column is stored as a scaled i128 from ingest through the
join and emitted as decimal128(p,s). 2^53+1 comes back as itself; so does
2^63+1, which the real demand path actually produces. The interim refusal
and its message go in the same PR, and the xfail pin flips.

Named ticket criteria this serves:

* the bit-exact criterion -- "a decimal128 static column serves
  bit-exactly (2^53+1 comes back as itself), schema decimal128(p,s)
  matching DuckDB": sections "The design" and "Boundary".
* the refusal-removal criterion -- "the interim refusal and its message
  are REMOVED in the same PR": section "Markers and text deleted".
* the pin-flip criterion -- "test_an_inexact_decimal_static_serves_exactly
  flips from xfail to a green parity test in the same PR": section "Test
  plan".

## Non-goals

* Decimal ARITHMETIC (lattice phase 5). Every arithmetic operator over a
  Dec value refuses by name after this lands.
* Ty::I128 as a frontend type / ::HUGEINT / out-of-i64 literals. Nothing
  demands them yet; the i128 MACHINE lane arrives without the type.
* DECIMAL ROW columns. They stay outside the row-schema vocabulary and
  keep refusing with the existing "row column 'v' has a non-scalar type".
  DuckDB serves them; that gap is unchanged by this ticket and, usefully,
  means the arrow ROW-ingest path needs no decimal arm at all.
* Bare decimal LITERALS staying f64 (packages/confit/docs/known-limitations.md:155-163).
  That row survives, and the fuzzer's "decimals" tag survives with it.

## DuckDB source (v1.5.5, pinned checkout)

1. Physical storage by precision -- `LogicalType::InternalType()`,
   src/common/types.cpp:100-117: DECIMAL is INT16 for width <= 4, INT32
   for <= 9, INT64 for <= 18, INT128 for <= 38, and an internal error
   above. The tier constants are `DecimalWidth<T>::max` in
   src/include/duckdb/common/types/decimal.hpp:16-45 (4 / 9 / 18 / 38),
   with MAX_WIDTH_DECIMAL = MAX_WIDTH_INT128 = 38.
2. Arrow round-trip -- `SetArrowFormat`, case LogicalTypeId::DECIMAL,
   src/common/arrow/arrow_converter.cpp:236-262. When
   `options.arrow_output_version <= ArrowFormatVersion::V1_4` the comment
   is explicit ("Before version 1.4 all decimals were int128") and
   bit_width is 128 regardless of tier; the format string is
   "d:" + width + "," + scale + "," + bit_width. The default is V1_0 --
   src/include/duckdb/main/client_properties.hpp:34,
   `ArrowFormatVersion arrow_output_version = ArrowFormatVersion::V1_0`.
   So DECIMAL(4,2) and DECIMAL(38,0) alike leave as decimal128(p,s),
   which cells I2/I3/E1 confirm live. Our boundary emits decimal128(p,s)
   for every tier; there is no decimal32/decimal64 output arm to write.
3. Comparison selection -- `BoundComparisonExpression::TryBindComparison`,
   src/planner/binder/expression/bind_comparison_expression.cpp:60-107.
   Equality-family predicates take `LogicalType::ForceMaxLogicalType`,
   ordering predicates `TryGetMaxLogicalType`; when the result is DECIMAL
   the width is recomputed as max_scale + max_width_over_scale, capped at
   Decimal::MAX_WIDTH_DECIMAL.
4. Which side casts -- `CastRules::ImplicitCast`,
   src/function/cast_rules.cpp: `ImplicitCastBigint` (:96-107) lists
   DECIMAL as a legal target; `ImplicitCastDecimal` (:196-204) lists only
   FLOAT and DOUBLE; `ImplicitCastDouble` (:187-194) lists only BIGNUM.
   `CombineUnequalTypes` (src/common/types.cpp:924-956) picks the cheaper
   direction and, when the target is DECIMAL, widens it through
   `DecimalSizeCheck` (:807-835). `LogicalType::GetDecimalProperties`
   (:730-795) gives BIGINT width 19 scale 0, INTEGER 10, SMALLINT 5,
   TINYINT 3, HUGEINT 38.
   Consequences, both reproduced live:
   * DECIMAL vs BIGINT: the BIGINT casts UP to DECIMAL. For a (38,0) key
     the comparison type is DECIMAL(38,0) and the cast is exact
     (cell D1/H1). For a (6,2) key it is DECIMAL(21,2) (19 + 2), also
     exact (cell H3).
   * DECIMAL vs DOUBLE: only decimal->double is a legal implicit cast, so
     the DECIMAL side casts DOWN to DOUBLE and the comparison is LOSSY
     (cells D2/H2/H4). D2 is the observable: probe 9007199254740992.0
     matches a static 9007199254740993.
   * Two DECIMALs unify by max(width - scale) + max(scale)
     (`CombineEqualTypes`, src/common/types.cpp:1069-1087).
5. DECIMAL -> DOUBLE, the exact algorithm -- `TryCastDecimalToFloatingPoint`,
   src/common/operator/cast_operators.cpp:2908-2924. Fast path when the
   unscaled integer is exactly representable OR scale == 0:
   `double(input) / DOUBLE_POWERS_OF_TEN[scale]`. Otherwise div/mod:
   `double(div) + double(mod) / DOUBLE_POWERS_OF_TEN[scale]`. This is NOT
   the same as Python's correctly-rounded float(Decimal), which is what
   our ingest uses today; the two agree only because the current guard
   admits nothing but f64-exact payloads. Any decimal->double we do after
   this lands must be this algorithm.
6. The capped-comparison trap. When the integer's decimal width plus the
   decimal's scale exceeds 38 the comparison width is capped (item 3) and
   the integer's cast can fail at run time. Live:
   `SELECT CAST(1 AS DECIMAL(38,30)) = 10000000000::BIGINT` raises
   "Conversion Error: Could not cast value 10000000000 to
   DECIMAL(38,30)", while `= 1::BIGINT` returns true.
7. Literal typing, unchanged and still ours-diverges: `typeof(0.5)` and
   `typeof(1.0)` are DECIMAL(2,1) (cell probe), which is
   packages/confit/docs/known-limitations.md:155-163's row and stays.

## The design: a Dec(p,s) type over a scaled i128 lane

Per the lattice spec's doctrine ("every `match` on `Ty` is forced by rustc
to answer for it"), the type is a real member, not a side channel:

```rust
pub enum Ty { I1, I8, I16, I32, I64, F64, Str, Dec(u8, u8) }  // p in 1..=38, s <= p
```

`Ty::lane()` returns `Dec(p,s)` unchanged (it IS a lane type, like F64);
`int_range()` and `is_int()` answer None / false. `Ty::name()` and
`arrow_ty_name()` stop returning `&'static str` -- they return
`Cow<'static, str>` so existing arms stay allocation-free and Dec renders
"dec(38,0)" / "decimal128(38, 0)". The IR text form gains a `dec(p,s)`
type token and a `const.dec(p,s) <i128>` literal, both round-tripping
through parse/print (the `parse(print(p)) == p` property already tested in
ir/tests.rs covers it).

Six moving parts:

1. INGEST TYPING. schema.rs stops prefix-matching. Under `Policy::Static`
   a field is `Ty::Dec(p, s)` when pyarrow says decimal32/64/128 with
   p <= 38 and s <= p; decimal256 stays `RowField::Opaque(name)` because
   DuckDB refuses it outright (cell I4). Row policy is untouched --
   decimal ROW columns stay opaque, which is why no arrow row-ingest arm
   is needed.
2. INGEST VALUES. `materialize_map` converts a Python `decimal.Decimal`
   to its scaled i128 exactly (`int(v.scaleb(s))` semantics, done on the
   Rust side from the value's sign/digits/exponent). No exactness guard,
   no f64 anywhere on this path. `ScalarVal` gains `Dec(i128)`.
3. JOIN KEYS: NO new key machinery. `KeyBits` is unchanged. The key lane
   stays the PROBE expression's type -- exactly the precedent already
   documented at packages/confit/src/specializer/frontend.rs:1367-1370
   ("the map key type (the key expression's type) becomes F64 and the
   build side is converted while the probe table is built"). `promote_key`
   (frontend.rs:1360-1378) gains two arms:
   * `(a, Ty::Dec(_, s)) if a.is_int()` -> key lane stays the integer
     lane. At materialize time a static decimal key converts to i64 only
     when it is exactly integral at that scale and fits; otherwise the
     build ROW IS DROPPED, because a non-integral decimal can never equal
     any integer probe. Dropping an unmatchable build row is already the
     established, semantics-preserving move for NULL `=` keys
     (duckdb/mod.rs:771). Justified by source item 4: the integer casts
     UP exactly, so equality is decidable at build time.
   * `(Ty::F64, Ty::Dec(_, _))` -> key lane stays F64; the static side
     converts with DuckDB's algorithm (source item 5), reproducing D2's
     loss rather than hiding it.
   The one arm that refuses: an integer probe against a decimal key whose
   `int_dec_width + s > 38` (source item 6). There DuckDB traps for large
   probes and serves for small ones; reproducing that needs a row-time
   trap the key path has no shape for, so it refuses by name. That needs
   scale >= 20 against a BIGINT probe -- no fit table produces it.
4. VALUE LANE. `StaticTy::Map { values }` carries `Ty::Dec(p,s)`;
   `Inst::Probe`'s dst (ir/mod.rs:860-866) is a Dec register; the
   left-miss NULL is the existing (validity, payload) pair with a
   `const.dec` zero payload. `RegVal` gains `Dec(i128)` (the enum grows
   from 24 to 32 bytes; the register frame is per-CALL and tens of slots
   wide, so this is noise). `ColData` gains no variant -- `ColData::new`
   answers `Ty::Dec` with `unreachable!`, and the reason is enforced by
   the row policy in part 1. Cranelift's `clif_ty` maps Dec to
   `types::I128`; `V::S` already carries a single cranelift value, so the
   `V::Str(CVal, CVal)` split is not needed. `Lit::Dec` builds by
   `iconcat` of two `iconst.i64` halves, since cranelift has no i128
   iconst.
5. TWO NEW INSTRUCTIONS, bought because refusing them would regress cells
   that are CORRECT today:
   * `Dtof { p, s }` -- Dec -> F64, DuckDB's div/mod algorithm verbatim
     (source item 5). Serves G9 (CAST AS DOUBLE) and Dec-vs-DOUBLE-lane
     comparisons.
   * `Itod { p, s }` -- integer lane -> scaled i128, with the range trap
     of source item 6 emitted ONLY when the comparison width is capped
     (otherwise the cast is provably in range and the trap is dead code).
     Serves `WHERE d = k` against an integer row column.
   Comparisons against CONSTANTS need no instruction at all: an integer
   or decimal literal folds into the column's own scale at bind time by
   exact i128 arithmetic. For `=`, a literal that does not divide down to
   the column's scale is constant-false; for `<`/`>` the floor/ceil at the
   column's scale is the exact equivalent bound. That is what keeps G5 and
   G6 green and makes them exactly right rather than accidentally right.
6. BOUNDARY. `OutCol` gains `Dec(Vec<(bool, i128)>)`. `pa_ty`
   (duckdb/arrow.rs:470-480) answers `pa.decimal128(p, s)`; `emit`
   (:531) writes the i128 slice straight into an arrow buffer, since
   x86-64 i128 little-endian IS arrow's decimal128 layout, the same
   `cast_bytes` shape the i64 lane uses. `infer_rows` builds
   `decimal.Decimal` with the SCALE PRESERVED -- Decimal('0.50'), not
   Decimal('0.5') -- because `duck_check` compares by `repr` and DuckDB's
   own `to_pylist` preserves it (cells G2, B1). `narrow_check`
   (duckdb/mod.rs:350-365) skips Dec via `int_range() == None`.

Everything else over a Dec value refuses by name, one message:

    unsupported: <op> over DECIMAL(<p>,<s>) column '<col>' -- decimal
    arithmetic and casts are m-8 lattice phase 5; this build serves
    DECIMAL statics, compares them, and emits them unchanged

covering: `+ - * / %`, CAST to any integer type, CAST to VARCHAR, any
scalar function taking a Dec argument, a UDF argument of Dec type,
coalesce/CASE/NULLIF unifying Dec with a non-identical type, and Dec
compared against a Dec of a DIFFERENT (p,s).

### The rejected alternative

Keep the value on an i64 lane -- `Dec(p,s)` typed at the frontend and
emitted as decimal128(p,s), but stored as a scaled i64, refusing by name
any payload whose scaled value does not fit 64 bits. It is a much smaller
diff: no cranelift i128 dependency, no `RegVal` growth, `OutCol::I64`
reused with only the arrow dtype changing, and it would still satisfy the
bit-exact criterion as literally written, because 2^53+1 fits i64
comfortably. It was rejected on cell F1: an ordinary fit-time
`sum(BIGINT)` measured 9223372036854775809 = 2^63+1, i.e. the epic's own
demand path routinely leaves i64, so the i64 lane would replace a refusal
with a differently-shaped refusal on exactly the query that motivated the
ticket -- and DuckDB stores DECIMAL(38,0) in INT128 anyway (source item
1), so the i64 lane is not the oracle's storage either. A hi/lo pair of
i64 lanes was considered as a way to dodge the cranelift i128 question
and rejected too: it doubles every lane-index relation (star order,
EXCLUDE, output naming, probe dsts) to buy back one already-verified
codegen capability (TASK-100).

## Behavior flips, each severity-classified

Severity ladder: (1) trap where DuckDB serves, (2) wrong value, (3) serve
where DuckDB refuses, (4) refuse where DuckDB serves.

1. FIXED, was sev 4 -- every A/B/C/D/E/F cell: an inexact decimal static
   stops refusing and serves the exact value with the decimal128(p,s)
   schema. This is the bit-exact criterion.
2. FIXED, was sev 4 -- cell I1: an inexact decimal column that the query
   never references stops blocking the build. The guard runs over every
   static column, referenced or not; removing it removes the over-reach.
3. FIXED, was sev 2 -- cells G1/G2/G3/I2/I3/I5: an f64-representable
   decimal stops coming back as a double. Note this is a visible output
   change for code that works TODAY: float -> decimal.Decimal, double ->
   decimal128(p,s). It is the oracle's answer, and it is what the
   bit-exact criterion asks for.
4. FIXED, was sev 3 -- cell I4: a decimal256 static column stops riding
   the f64 lane and becomes an opaque type, refusing by name when
   referenced. DuckDB refuses it at arrow register at any precision.
5. TRADED, sev 2 -> sev 4 -- cells G7/G8/G10/G11/G12/G13: arithmetic,
   CAST to integer, CAST to VARCHAR, and coalesce/CASE unification over a
   decimal column stop producing a silently wrong double and refuse by
   name. G10 and G11 are wrong VALUES on master today (0.50::BIGINT is 0
   here, 1 in DuckDB; '0.5' vs '0.50'), so this is the ladder's own
   preference, and it is the lattice spec's rule verbatim: "an entry point
   we haven't bought refuses by name, never approximates."
6. NEW, sev 4, narrow -- a decimal static key with scale >= 20 joined
   against an integer probe refuses by name. DuckDB traps there for large
   probes (source item 6) and serves for small ones; the row-time trap is
   phase 5. Unreachable from any fit-table shape.
7. NO CHANGE, must stay green -- cells G5, G6, G9, H1, H2, H3, H4, D1,
   D2, D4, G4, E2: WHERE equality and ordering against constants, CAST to
   DOUBLE, and every join-key combination keep their current answers. The
   design buys `Dtof`, `Itod` and the bind-time constant fold precisely so
   that none of these becomes a refusal.
