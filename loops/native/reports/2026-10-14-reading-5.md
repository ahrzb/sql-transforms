# Native catalog, reading 5 (2026-10-14)

## 0. What this is {#what-this-is}

This is the native catalog's fifth milestone report. It names the master
commit `44052cf` of 2026-10-14. The previous report is
[reading 4](2026-10-06-reading-4.md), on the master commit `627abf0` of
2026-10-06. T19 to T29 are the loop's tickets
([`tickets.md`](../tickets.md)), and a number such as #437 is a PR. The
owner paused the loop from 2026-10-06 16:11 UTC to 2026-10-14 10:07 UTC.

This report has a cross-loop trigger. confit's #430 builds the input
guard of a catalog entry once. Before #430, confit built the guard again
each time a query read a field of the entry's output. On #430, T28 (#437)
made 13 forests, 36 spline configurations and 2 wide one-hot encoders
native ([section 6](#needs-from-confit)).

Every measurement ran with confit's release build, with the commands of
reading 4 and the additions in [section 8](#environment-and-repro). Two
things changed on the machine since reading 4, apart from the code:

- The Nix dev shell (#428) gives the project's Python environment the
  CPython 3.14.7 of Nix. Reading 4 used uv's CPython 3.14.6.
- This machine serves reading 4's own code more slowly than reading 4's
  machine did. On this machine, the native calls of reading 4's code take
  a median of 1.22 times the time that reading 4 measured. Its twin calls
  take 1.26 times.

So [section 3](#speed) also measures reading 4's code on this machine,
with reading 4's Python, and gives the deltas of the code alone.

Since reading 4, 11 native PRs merged, all of them tickets:

- `to_native` serves a bound above 0 only with `allow_bound=True` (T19,
  #414);
- the fixture generator draws ±inf, and `check` fails on no row (T20,
  #415);
- the spline on confit's binding of a value once (T21, #416);
- one CASE per tree for the forests (T22, #420);
- an output field that has the same value in every instance reads no
  instance id (T23, #418);
- a parity bound as an error scale, held by `check` (T24, #421);
- the input guard (T25, #423);
- the forest and spline build estimates count the input guard (T26, #427);
- the encoders' input guard is one test for each feature (T27, #429);
- the forest and spline build estimates fitted again on confit #430 (T28,
  #437);
- the kernel probe draws random significands (T29, #439).

A step can hold several fitted instances of one transformer, and each row
names its instance by an instance id.

The confit loop merged 11 PRs in this time. Seven changed confit: #412,
#417, #419, #422, #425, #426 and #430. Two triaged its nightly runs (#424
and #438), and two were reports (#413 and #436). The owner merged #428, the
Nix dev shell. The owner also pushed two refactors of the model code of
`sql_transform` and four commits of docs. The last of them (`b4b8d03`)
moved the coverage table and the catalog contract (the rules that every
catalog entry follows) to `packages/sql-transform/spec/native/`. After
`44052cf`, the confit loop merged #440 to #442. This report does not

## 1. What moved {#what-moved}

**Where the twin raises an error, the entry now raises one too.**
- T25 (#423) builds the closed record
  [tolerated-differences.md](../decisions/closed/tolerated-differences.md).
  Before T25, an entry answered some rows on which its twin raises, for
  example ±inf in a scaler.
- Each entry now has an input guard. To build it, the catalog probes the
  twin from one row that the twin accepts: each feature in turn at ±inf,
  NaN and NULL. The families add the tests that this probe cannot find,
  for example Box-Cox at x ≤ 0 and an encoder's unknown categories.
- The guard puts its tests into the first output field, as a CASE. On a
  row where a test holds, that field raises an error, and the call fails.
- Over seeds 0 to 19 of the parity test, the twin raised on 8,965 of
  140,240 rows (6.4%). The entry trapped on each of these rows
  ([section 4](#exactness)).
- The widest step of a class is the test step with the most output
  fields that the catalog serves. On the widest step of each class, the
  guard costs a median of 8% of a 64-row call. `OneHotEncoder` pays the
  most, 60%.
- A `Pipeline`'s guard also tests the input of each later step. The
  widest `Pipeline` step builds 4.4 times as long with the guard as
  without it (finding 69).

**The default `RandomTreesEmbedding` serves a row 3.8 times as fast as
reading 4's code, and forests of up to about 5,990 output fields serve.**
- T22 (#420) spells each tree as one CASE, which answers the node id of
  the row's leaf. Every output field of the tree reads that CASE, and
  confit computes it once for each row (confit #412).
- The default forest has 100 trees of depth 5 and 2,292 output fields.
  It builds in 1.8 s and serves a row in 190 µs, against the twin's
  21,109 µs (111x). On this machine, reading 4's code builds it in 4.8 s
  and serves a row in 716 µs.
- Reading 4 capped a forest at 25,000 path steps. A path step is one
  branch test on the path to a leaf. The cap is now an estimate of the
  build in seconds, fitted on measured builds (T26, #427, and T28, #437).
- Over 8 features, forests serve up to about 5,990 output fields. Three
  forests past reading 4's cap now serve. One has 250 trees of depth 5
  (27,014 path steps). The other two have one tree of unbounded depth,
  fitted on 2,000 or 4,000 rows (39,835 and 90,139 path steps).
  `to_native` takes 8.0 s, 1.3 s and 3.6 s for them.

**Splines of degree 4 and 5 serve at widths that stayed Python at reading
4.**
- confit binds once a value that a SQL function body reads twice or more
  (#412). So the spline's expression no longer doubles with each degree in
  the build. T21 (#416) and T28 (#437) fitted the build estimate again.
- At reading 4, degree 5 at 7 knots stayed Python from 22 features with
  `continue`, from 32 with `periodic` and from 64 with `constant`. Degree
  4 at 64 features with 5 knots and `continue` also stayed Python. These
  four now serve, and `to_native` takes 1.8, 1.9, 4.5 and 2.8 s for them.
- 16 features of degree 5 with 7 knots and `continue` build in 1.05 s,
  against 5.10 s for reading 4's code on this machine.
- Of the 359 configurations that T28 measured, 7 stay Python, all of 96
  or 128 features. They build in 8.0 to 12.5 s.

**A configuration within a bound above 0 serves only if the caller asks
for it.**
- Since T19 (#414), `to_native(step)` serves bit-exact entries only
  ([matvec-parity-bound.md](../decisions/closed/matvec-parity-bound.md)).
  With `allow_bound=True`, it also serves Box-Cox (4 ulps) and
  `FunctionTransformer` with `exp`, `log`, `log2`, `log10`, `tan` and
  `cbrt`, each within its bound.
- If the step stays Python, `explain_native` names the instance and the
  bound that kept it there.
- The kernel probe (`function.kernel_distance`) measures the largest
  distance in ulps between numpy's function and confit's, on 40,000
  random values and the edge values. If the probe reads 0 for a function
  on a machine, the function is bit-exact there. It then serves by
  default, and a composition such as a `Pipeline` can hold it. On this
  machine, the probe reads above 0 for all six functions.
- T24 (#421) lets a family declare its parity bound as an error scale.
  `check` holds each row to it. No entry declares one yet.

**The parity test now sends ±inf, and it fails a step on which it compares
no row.**
- T20 (#415) adds ±inf to the edge values of the fixture generator. The
  gate did not see reading 4's breach of the periodic spline (finding 51)
  because it drew no ±inf. At ±inf, that spline's twin answers NaN, and
  the entry answered 0.0 on some output fields. In the gate's 8 seeds,
  1,661 of 56,320 rows hold ±inf (T20).
- The 200-seed parity run passed 35,055 steps with no failure and 145
  named skips, as at reading 4.
- T29 (#439) changed the draws of the kernel probe. The probe reads as at
  reading 4 ([section 4](#exactness)).

**The native entries serve the widest steps a median of 84 times as fast
as their twins, against 77 times at reading 4.**
- In the dev shell, a native call of a widest step takes a median of
  1.32 times reading 4's time. A twin call takes 1.51 times.
- Most of this is the machine and the Python. On this machine and on uv's
  CPython, master's native calls take a median of 1.02 times the time of
  reading 4's code.
- On the CPython of Nix, a twin call takes a median of 1.23 times its
  time on uv's CPython. A native call takes 1.05 times
  ([section 3](#speed)).

**What changed since reading 4.**
- **This machine is slower.** On this machine, a native call of reading
  4's code takes a median of 1.22 times as long as on reading 4's machine
  (0.98 to 1.60). A twin call takes 1.26 times as long (0.95 to 1.75).
- **On the median, the code changed little.** On the same machine and
  Python, master's native calls take a median of 1.02 times the time of
  reading 4's code (0.39 to 2.00). The twin calls take 1.00 times.
- **Six classes serve faster in every run.** For each of them, every run
  of master is faster than every run of reading 4's code. They are
  `RandomTreesEmbedding` (2.6 times as fast, one CASE per tree),
  `ColumnTransformer`, `FeatureUnion`, `OneHotEncoder`,
  `QuantileTransformer` and `PolynomialFeatures`.
- **Eight classes serve more slowly in every run.** With master, the widest
  `Pipeline` step serves a call in 5.9 to 10.8 ms. With reading 4's code,
  it serves a call in 5.0 to 5.8 ms (finding 69). `SelectKBest`,
  `SelectPercentile`, `SelectFpr` and `SequentialFeatureSelector` take 10
  to 110 µs more for each call. They compute 1 to 8 output fields from 10
  to 21 features, and their input guard makes a call 1.15 to 1.32 times as
  long. `MaxAbsScaler`, `RFECV` and `KBinsDiscretizer` take 4 to 12% more.
- **The input guard costs a median of 8% of a call.** This reading also
  built each widest step without its guard's tests. It served the two
  builds in alternate rounds. With the guard, a call takes 0.79 to 1.60
  times the time without it. The most are `OneHotEncoder` (1.60),
  `OrdinalEncoder` (1.39), `Pipeline` (1.33) and `SelectKBest` (1.32).
  `KBinsDiscretizer` serves faster with the guard (0.79), and this reading
  did not find the cause.
- **The guard lengthens the build of the widest `Pipeline` most.** 8
  steps build in 0.05 s or more without the guard. With the guard, the
  median of them builds 1.2 times as long. The widest `Pipeline` builds
  4.4 times as long (finding 69). `FeatureUnion` and
  `KBinsDiscretizer` follow, at 1.5 times.
- **The CPython of Nix serves the twins more slowly.** On master, the
  twin calls in the dev shell take a median of 1.23 times their time on
  uv's CPython (0.98 to 1.67). The native calls take 1.05 times (0.67 to
  1.64). Nix builds its CPython without profile-guided optimization, and
  uv's CPython has it.

**Delivered since reading 4:**

   (`struct-field-reads`, the rest of finding 60). For 100 trees of depth
