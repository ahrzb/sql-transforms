# Native catalog, reading 4 (2026-10-06)

## 0. What this is {#what-this-is}

This is the native catalog's fourth milestone report. It covers waves 4
to 6 and names the master commit `627abf0` of 2026-10-06. The previous
report is [reading 3](2026-10-06-reading-3.md), on the master commit
`87636ef`. T11 to T19 are the loop's tickets ([`tickets.md`](../tickets.md)),
and a number such as #403 is a PR.

Every measurement ran with confit's release build, on code equal to
`627abf0`'s, plus this report's fix of the bench (finding 55).
[Section 8](#environment-and-repro) gives the commit of each measurement.
The commits between them change only docs, decision records and the text
of two `NotNative` messages.

The commands are reading 3's, with two additions:
- T15 (#399) changed the fixture generator, the code in `catalog_test.py`
  that draws the fitted steps and the request rows of the parity test. It
  now draws boolean features, so every class's widest step changed.
  [Section 3](#speed) therefore also measures reading 3's own steps again,
  drawn with the generator of before T15.
- A count of the rows that the parity test compares
  ([section 4](#exactness)).

Since reading 3, 16 native PRs merged:
- eight tickets: a bound for each configuration and five
  `FunctionTransformer` functions (T11, #388), `QuantileTransformer` as one
  search tree per feature (T12, #391), the spline's build estimate fitted
  again (T13, #396), `np.cbrt` (T14, #394), boolean features in the fixture
  generator (T15, #399), `KBinsDiscretizer(dtype=np.float32)` (T17, #402),

- reading 3 (#395), its correction (#410), and the loop docs in simple
  English (#408);
- four updates of the ticket board (#393, #397, #400, #407).

The repository also gained the `simple-english` skill and `GLOSSARY.md`
(#401). #405 removed the prose checker of #401. The confit loop merged #392
and #398.

## 1. What moved {#what-moved}

**`RandomTreesEmbedding` serves natively and bit-exact, so
`sklearn.ensemble` has no "not yet" row left.**
- T16 (#403) serves `RandomTreesEmbedding(sparse_output=False)`. The twin
  rounds each feature to float32 and walks each tree to a leaf. Each output
  field is 1.0 at one leaf and 0.0 elsewhere.
- The entry tests each leaf's path. It moves each threshold to the double
  that splits the doubles as the float32 comparison does, so it uses only
  comparisons and constants. The 200-seed parity run checked 1,400 of
  1,400 steps.
- The default forest, 100 trees of depth 5, has 2,292 output fields on
  this reading's fit. It builds in 4.3 s and serves a row in 581 µs,
  against the twin's 18,461 µs (32x).
- The default `sparse_output=True` stays Python, because its output is
  sparse.
- Coverage is 31 of 68 in-scope transformers, up from 30.

**A periodic spline answered 0.0 where its twin answers NaN. Reading 3
had called the spline entry bit-exact.**
- The case: `SplineTransformer(extrapolation="periodic",
  handle_missing="zeros")` with a feature at ±inf. With
  `handle_missing="zeros"`, sklearn does not reject an infinite feature.
  At ±inf the twin answers NaN on every output field.
- The entry answered 0.0 on some output fields instead: those with no
  basis function in the last interval between the knots.
- This reading probed the 398 spline configurations that the entry serves
  over two features, at ±inf, NaN, NULL, ±1e308, ±0 and 1.5. On the spline
  code before #406, 22 parted from the twin. On master, none part
  (finding 51).
- #406 (T18) fixed it, and a fixture of this case joined the parity test.
- Reading 3's parity run could not find it, because the fixture
  generator draws no ±inf (finding 52). The research for #404 found it with a probe
  at ±inf.

**Encoders and pipelines serve boolean features, and every class is
tested on them.**
- T15 (#399) draws 15% of the features as booleans, and 7% of the steps
  take boolean features only.
- `OneHotEncoder`, `OrdinalEncoder` and `TargetEncoder` refused any boolean
  feature before. They now serve it bit-exact. So does a `Pipeline` that
  passes booleans from one step to the next.
- The first 200-seed run of T15 found encoders that parted from their twin
  on rows of booleans with a NULL (finding 57). #399 fixed them before it
  merged.
- Five `FunctionTransformer` functions stay Python over boolean features
  only, because numpy answers them in another type: `reciprocal` (int8),
  and `exp`, `sin`, `cos` and `tan` (float16). They are this reading's 145
  skips ([section 4](#exactness)).

**`QuantileTransformer` builds 2.4 to 3.6 times faster, and its cap
doubled to 8,000 quantiles.**
- T12 (#391) spells each feature as one search tree whose leaves compute
  both of the twin's lines. Before, the entry built two trees.
- One feature builds in 0.65 s at 1,000 quantiles (1.58 s at reading 3)
  and in 1.32 s at 2,000 (4.71 s). It builds in 3.01 s at 4,000 and in
  6.74 s at 8,000.
- The cap is now 8,000 quantiles summed over an estimator's features, up
  from 4,000. So the default of 1,000 quantiles serves up to eight
  features.
- Reading 3's widest step, three instances over 27 features, serves 64
  rows in 750 to 805 µs, against 1,003 µs at reading 3.
- The catalog no longer needs confit's "two CASE trees"
  ([section 6](#needs-from-confit)).

**`FunctionTransformer` serves `exp`, `log`, `log2`, `log10`, `tan` and
`cbrt`, each within an ulp bound of 1 to 3.**
- T11 (#388) lets a class declare a bound for each configuration. T14
  (#394) adds `cbrt`, on confit #390.
- numpy picks its code for these functions by CPU. On a CPU with AVX-512
  (a set of x86 vector instructions), numpy uses its own code. DuckDB and
  confit call glibc's functions.
- So a function serves only where a probe finds numpy within the
  function's bound of confit. The probe (`kernel_distance` in
  `function.py`) runs at first use, on about 40,000 values. On this reading's
  machine it read 1 ulp for five functions and 3 ulps for `cbrt`.
- Over the rows of the 200-seed parity run, the largest distance is 1 ulp
  for `exp`, `log`, `log10` and `tan`. It is 0 for `log2` and 3 ulps for
  `cbrt` ([section 4](#exactness)).
- At 128 features, `np.exp` serves a row in 10.0 µs, against the twin's
  205 µs (21x).

**Splines of 32 features at degree 3 now serve, and so does
`KBinsDiscretizer(dtype=np.float32)`.**
- T13 (#396) fitted the spline's build estimate again, after confit #387
  made spline builds about 4 times faster. 32 features at degree 3 with 8
  knots build in 1.0 to 2.3 s with `continue`, `constant` and `periodic`.
  Reading 3 refused the `continue` one, at an estimated 22 s.
- T17 (#402) serves `KBinsDiscretizer(dtype=np.float32)`, bit-exact. The
  twin rounds each feature to float32 before it compares it with the
  float64 bin edges. The entry moves each edge to the double that splits
  the doubles in the same way.
- 32 float32 features of 31 bins, one-hot, build in 1.00 s and serve a row
  in 200 µs, against the twin's 4,937 µs (25x). The float64 configuration
  serves in 198 µs.

## 4. Exactness {#exactness}

**Two classes serve configurations within an ulp bound above 0,** up from
one at reading 3. Every other entry is registered at 0 ulps, including
`RandomTreesEmbedding` and the float32 `KBinsDiscretizer`.

| family | configuration | bound | largest distance measured | reason |
|---|---|---|---|---|
| `PowerTransformer` | Box-Cox, `standardize=False` | 4 ulps | 3 ulps, 400 steps, 14,464 rows | DuckDB has no `expm1`, so the entry spells it from `exp` and `ln` |
| `FunctionTransformer` | `np.exp` | 1 ulp | 1 ulp, 364 steps | numpy's AVX-512 kernel is not glibc's, which DuckDB calls |
| `FunctionTransformer` | `np.log` | 1 ulp | 1 ulp, 400 steps | the same |
| `FunctionTransformer` | `np.log2` | 1 ulp | 0, 400 steps | the same |
| `FunctionTransformer` | `np.log10` | 2 ulps | 1 ulp, 400 steps | the same |
| `FunctionTransformer` | `np.tan` | 1 ulp | 1 ulp, 368 steps | the same |
| `FunctionTransformer` | `np.cbrt` | 3 ulps | 3 ulps, 400 steps | the same |

The distances are measured on the steps and rows of the 200-seed parity
run (seeds 0 to 199, 2026-10-06). **For Box-Cox, the largest distance on
the fixtures rose from 2 ulps at reading 3 to 3 ulps,** inside its bound
of 4. T15 changed the draws, so the rows are new.

**The parity run.** It covers 200 seeds of every fixture configuration:
176 configurations of 34 classes, in one pytest run on 4 workers (30 min
21 s).
- 35,055 steps were each checked row by row against their twin, and
  against their own definition run on DuckDB.
- There were 0 failures and 145 skips. Each skip is a named refusal:
  `FunctionTransformer` over boolean features only, with `reciprocal`
  (42), `exp` (36), `tan` (32), `cos` (19) or `sin` (16).
- Delta since reading 3: then 150 configurations of 33 classes, 30,000
  steps, and 0 skips. The 26 new configurations are 12 of
  `FunctionTransformer`, 7 of `RandomTreesEmbedding`, 6 float32 ones of
  `KBinsDiscretizer` and the periodic spline of T18.

**The rows that the parity test compares.** The parity test compares a
row only where the twin answers it. Over seeds 0 to 19, the twin raised an
error on 6,866 of 140,240 rows (4.9%), so the test did not compare those
rows. The classes
with the largest shares are `OrdinalEncoder` (21.2%), `OneHotEncoder`
(20.8%), `PowerTransformer` (10.2%), and `IsotonicRegression` and
`SplineTransformer` (8.6% each). Every step compared at least one row.
These rows are the subject of the input guard ([section 7](#left-open)).

**The order pins of the new configurations.** Each one pins its twin's
order in its own tests:
- `RandomTreesEmbedding`: every threshold, the float32 values beside it,
  its cutpoint and the doubles beside the cutpoint, the signed zeros, the
  subnormals, ±float32 max, values past float32's range, ±inf and NaN.
